# DineFlow Phase 28 — Kitchen Workflow Reliability

## Scope and boundaries
Reliable kitchen preparation, waiter handoff acknowledgment, bounded recovery after network uncertainty and long-lived kitchen display synchronization. This phase does **not** introduce payments, automatically retry mutations, or claim real hardware validation.

## Delivered
1. **Authenticated, versioned, explicit waiter pickup receipt** `POST /api/orders/tickets/:id/pickup-ack`. Only the waiter currently assigned to the *open visit* can confirm they physically received food after the kitchen marked it `picked_up`. Receipt is durable (`pickup_acknowledged_at/by`), separately audited (`waiter.pickup_acknowledged`), and increments the ticket version so concurrent kitchen reminders, waiter serving and third-party updates cannot act on an old state. A confirmed receipt can be safely replayed by the same currently assigned waiter and returns `already:true` without a second audit event; revocation/reassignment is always checked before replay. Owner, kitchen, cashier and other-tenant accounts cannot impersonate the waiter. Receipt does **not** mean food was served; existing waiter Serve stays independently authorized and versioned, and does not require this optional acknowledgment for backward compatibility.
2. **Authoritative kitchen per-ticket reconciliation** `GET /api/orders/kitchen/tickets/:id/state`: owner/manager/kitchen only; scoped tenant/location query inside a PostgreSQL transaction with a row-level share lock. Contains latest ticket status, version, line progress, handed-off/receipt/served timestamps and **read-notification** timestamp for the current assigned waiter. Reading a notification means *viewed*, not *picked up* or *served*. The endpoint never mutates the ticket and has `Cache-Control:no-store`.
3. **No blind POST replay after ambiguous outcomes**. All kitchen actions first verify server state/version before sending a single confirmed write. Existing optimistic concurrency checks remain server-side; a 409 requires new state inspection, not automatic resubmission. Transport/5xx errors after a POST is attempted persist a bounded account/restaurant-scoped list of potentially committed ticket actions in local storage. Those tickets are blocked until the operator explicitly calls the server reconciliation endpoint and reviews the verified result, even after page navigation/reload. A read failure is never treated as a submitted mutation; nonambiguous failures such as reminder throttle do not become fake successes.
4. **Commit-ordered replay cursor**. `orderChanged` acquires the per-location revision row update lock before inserting its outbox event, so concurrent transactions cannot allocate event cursors that commit in the opposite order. New kitchen-only, non-cached `GET /api/orders/kitchen/watermark` obtains the revision row share lock before reading the scoped maximum cursor; the UI initializes the cursor *before* loading its first complete page. Replay of `/api/orders/changes?after=...` validates strictly increasing event sequences and processes at most eight 50-event pages per cycle, continues if more remain, and never advances an invalid response. Events are **invalidation hints**, not command replay; the visible queue is always refreshed from authoritative, tenant-scoped GETs.
5. **Connectivity and state clarity**. SSE revision events plus 12-second cursor polling, foreground resync, no background write queue, independent connection/replay status, and manual Recheck Changes. Ticket detail now shows kitchen handoff, waiter acknowledgment, notification-view state and final service as distinct facts. Kitchen cards show when the waiter has explicitly acknowledged pickup, not misleading “served” statuses. Native waiter order detail has a real Confirm Kitchen Pickup action, clear prompt, busy state and uncertain-outcome refresh safeguard, localized to English/Dari/Pashto with RTL.
6. **Additive migration** `0013_phase28_pickup_ack.sql`, journal entry, updated schema and API integrations. No npm dependencies added. Historical handoffs remain unacknowledged rather than manufacturing evidence. All existing billing, kitchen and serving states remain unchanged.
